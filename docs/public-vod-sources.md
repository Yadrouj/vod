# منابع جدید فیلم و سریال و به‌روزرسانی آرشیو

منابع درخواست‌شده در ۳۱ اکتبر ۲۰۲۶ در `scripts/public-vod-sources.mjs`
ثبت شده‌اند. این اتصال فقط صفحه‌ها و APIهای عمومی را می‌خواند؛ ورود، اشتراک،
کپچا، لینک خصوصی و نصب یا مهندسی معکوس برنامه لازم نیست و انجام نمی‌شود.
وجود نام سایت در فهرست، به معنی دریافت موفق تمام لینک‌های آن نیست.

| منبع | روش بررسی |
|---|---|
| `bamabin.com` | بررسی دسترسی و مجموعه‌های عمومی WordPress؛ خطای شبکه ثبت می‌شود |
| `9movie.tv` | آدرس فعلی بررسی‌شده `9movie.info`؛ مجموعهٔ عمومی `movies` و نمونهٔ صفحات دانلود |
| `seenta.watch` | بررسی صفحهٔ عمومی و لینک‌های عنوان؛ موتور جستجو/برنامه به‌عنوان فایل فیلم وارد نمی‌شود |
| `movie-chi.ir` | صفحهٔ معرفی اپلیکیشن؛ APK/EXE لینک فیلم نیست |
| `familymovie.tr` | صفحه‌بندی عمومی `/api/media` و جزئیات `/api/media/single?id=...` |
| `yekmoviez.com` | بررسی دسترسی و صفحهٔ معرفی برنامه؛ بدون استفاده از ربات یا حساب دیگران |
| `nightmovie.org` | نمونهٔ صفحات عمومی عنوان؛ فایل بدون لینک عمومی وارد نمی‌شود |

اگر منبعی غیرقابل‌دسترسی باشد یا فایل عمومی نداشته باشد، همان وضعیت در گزارش
ثبت می‌شود؛ هیچ فایل، کیفیت، قسمت، امتیاز IMDb یا لینک حدسی ساخته نمی‌شود.
برای منابعی که دانلود عمومی در نمونه‌های بررسی‌شده ندارند، اسکن تمام صفحات
متن به‌عنوان «دانلود کامل آرشیو» گزارش نمی‌شود.

## اجرا

```bash
# به‌روزرسانی روزانهٔ محدود، ادغام و ساخت صفحات و فهرست‌های سایت
npm run scrape-public-vod

# بررسی کامل منابع عمومی قابل‌استخراج؛ ادامه از checkpoint قبلی
npm run scrape-public-vod:full

# فقط جمع‌آوری، بدون تغییر کاتالوگ اصلی
node scripts/scrape-public-vod-sources.mjs --full
```

هم‌زمان دو فرایند ادغام‌کنندهٔ کاتالوگ اجرا نکنید. ابتدا sync فعلی فیلم تمام
شود، سپس `refresh-public-vod`، F2MY یا ادغام منابع منتخب اجرا شود.

خروجی‌ها در `.media-cache/public-vod/`:

- `report.json`: وضعیت واقعی هر هفت منبع، تعداد صفحات، جزئیات، عنوان‌ها و لینک‌ها؛
- `state.json`: cursor صفحه‌بندی و زمان بررسی هر عنوان؛
- `source.json`: دادهٔ قابل‌ادغام؛ شامل امضا و زمان انقضای لینک در صورت وجود؛
- `merge-report.json`: عنوان‌ها و لینک‌های اضافه/تازه‌شده پس از ادغام.

وضعیت `partial` یعنی بررسی کامل نشده و باید دوباره اجرا شود. `unavailable`
خطای اتصال/HTTP است؛ `no-public-downloads` فقط نتیجهٔ صفحات نمونه است، نه
ادعای بررسی تمام عنوان‌های آن سایت. `app-or-search-only` یعنی صفحهٔ عمومی
لینک دانلود فیلم قابل‌استخراج نداشته است.

## تطبیق و حفظ داده

- تطبیق بر اساس IMDb صریح یا نام کامل + سال + نوع فیلم/سریال انجام می‌شود.
  تطبیق مبهم کنار گذاشته می‌شود؛ فیلم و سریال هم‌نام یکی نمی‌شوند.
- کیفیت، نوع زیرنویس/دوبله، فصل، قسمت و نام فایل حفظ می‌شود.
- لینک منابع قبلی، پوسترها، اطلاعات IMDb و آرشیو قسمت‌ها حذف نمی‌شود.
- لینک امضاشده بدون تغییر توکن ذخیره می‌شود؛ فایل منقضی یا با کمتر از شش ساعت
  اعتبار وارد نمی‌شود. امضاهای جدید همان فایل جای امضاهای قبلی را می‌گیرند.
- امتیاز کاربران منبع به‌جای امتیاز IMDb ثبت نمی‌شود.
- تریلر، پیش‌نمایش، فایل خالی پلیر و نصاب برنامه وارد لینک دانلود فیلم نمی‌شود.
- وجود `format=mp4` در query دلیل ویدئویی بودن یک صفحهٔ HTML نیست.
  صفحه‌های واسطهٔ GapFilm در `externalDownloadPages` حفظ می‌شوند، نه به‌عنوان فایل مستقیم پلیر.
  خروجی HEAD تأییدشدهٔ HTML یا 404/410 هم می‌تواند به `unavailableDownloadLinks` منتقل شود.
  خطای شبکه یا 403 به‌تنهایی مبنای حذف فایل نیست؛ ممکن است محدودیت جغرافیایی باشد.
- محدودیت حق نشر `tt33184638` / Paris Has Fallen برقرار می‌ماند.

## اجرای شبانه

کار مستقل `public-video` به زمان‌بند فعلی اضافه شده است: **۰۳:۰۰ تا قبل از
۰۷:۰۰ تهران**، همراه تریگر روزانهٔ موجود. این کار پس از منابع منتخب اجرا
می‌شود؛ خاموش بودن DonyayeSerial مانع اجرای مستقل آن نیست. تنظیمات ذخیره‌شدهٔ
داشبورد با حفظ ساعت‌ها و منابع غیرفعال، کار جدید را دریافت می‌کنند.

بودجهٔ پیش‌فرض کار جدید ۳۰ دقیقه (شامل ادغام و ساخت فهرست‌ها)، حداکثر جزئیات روزانه ۵۰۰ عنوان و فاصلهٔ درخواست
۹۰۰ میلی‌ثانیه با حداکثر دو درخواست هم‌زمان است. این سقف، بازبینی روزانهٔ
آرشیو فعلی FamilyMovie و تازه‌سازی URLهای امضاشده را ممکن می‌کند. برای افزودن
این کار، بودجهٔ کارهای تصویرِ قابل‌ادامه تنظیم شده تا مجموع همچنان چهار ساعت باشد.
اسکن کامل تاریخچه را یک‌بار جدا اجرا کنید؛ هر شب همهٔ
صفحات قدیمی دوباره خوانده نمی‌شوند. محدودیت robots.txt رعایت می‌شود.

```dotenv
PUBLIC_VOD_DETAIL_LIMIT=500
PUBLIC_VOD_REQUEST_GAP_MS=900
PUBLIC_VOD_TIMEOUT_MS=15000
PUBLIC_VOD_BUDGET_MS=1500000
# اختیاری: فقط برخی منابع (شناسه‌ها در فایل رجیستری)
PUBLIC_VOD_SOURCE_IDS=familymovie,9movie
```

برای دوام checkpoint، `.media-cache` باید مثل کش فعلی اسکریپرها روی volume
پایدار باشد. قبل از انتشار دادهٔ چندروزه، `npm run scrape-public-vod:full`
یا refresh لازم را اجرا کنید: URLهای FamilyMovie می‌توانند منقضی شوند.

پوشهٔ `public/data/titles/` در Git نیست؛ حتی اگر `title-map.json` با commit
تازه دریافت شود، فایل‌های جزئیات باید متناسب با کاتالوگ بازسازی شوند. روی سرور
دارای bind mount، صرفاً build کردن image فایل‌های قدیمی میزبان را تازه نمی‌کند.
پس از پشتیبان‌گیری، دریافت LFS و ساخت image جدید، پیش از بازکردن ترافیک:

```bash
docker compose --env-file .env.local -f docker-compose.prod.yml run --rm --no-deps maintenance node scripts/build-vod-title-files.mjs
docker compose --env-file .env.local -f docker-compose.prod.yml run --rm --no-deps maintenance node scripts/build-vod-index.mjs
# اگر از زمان دریافت لینک‌ها گذشته است، ابتدا URLهای امضاشده را تازه کنید:
docker compose --env-file .env.local -f docker-compose.prod.yml run --rm --no-deps maintenance node scripts/refresh-public-vod.mjs
```

نام فایل Compose باید با استک واقعی میزبان منطبق باشد. worker دیگری را
هم‌زمان با این مراحل روی همان کاتالوگ اجرا نکنید.

## اصلاح سازگاری آرشیو قبلی

آرشیو تک‌صفحهٔ DonyayeSerial در اکتبر ۲۰۲۶ به‌جای `start_year` سال واقعی را
در عنوان گذاشته است. parser هر دو ساختار و عنوان سریال بدون سال را می‌پذیرد.
کنترل حداقل تعداد عنوان/لینک و حفاظت در برابر کوچک‌شدن غیرعادی باقی مانده است.
checkpoint و گزارش پیشرفت پوشه‌های قسمت‌ها هر ۱۰ عنوان ذخیره می‌شود.
فایل قسمت به‌عنوان پوشه خزیده نمی‌شود: صد فایل در یک پوشه فقط یک ریشهٔ
یکتا دارند. خروجی این مرحله هم بدون حذف فایل زنده به‌صورت atomic جایگزین می‌شود.

برای قطعی موقت API متادیتای غنی، می‌توان `VOD_SYNC_SKIP_API=1` داد؛ این گزینه
فقط enrichment اختیاری عکس/متن را رد می‌کند، نه دانلودها یا متادیتای رسمی IMDb.
پیش‌فرض `VOD_SYNC_API_LIMIT=50` مانع صف چند‌هزاردرخواستی در یک شب می‌شود؛
برای backfill جداگانه می‌توان این سقف را افزایش داد.

sync روزانهٔ قبلی نیز سقف مستقل ۱۰۰ پوشهٔ سریال، ۱۲۰ گروه فیلم Moviesho و
۴۰ سریال Moviesho دارد؛ فهرست اصلی DonyayeSerial همچنان کامل خوانده می‌شود.
برای backfill کامل جداگانه، `VOD_SERIES_EXPAND_LIMIT=0`،
`MOVIESHO_MOVIE_GROUP_LIMIT=0` و `MOVIESHO_SERIES_LIMIT=0` قابل تنظیم است.
تازه‌سازی صفحات تغییرکردهٔ Moviesho/ZardFilm علاوه بر این مرحله، در کار مستقل
`curated-video` انجام می‌شود.
وجود یک عنوان در آرشیو دیگر باعث کنارگذاشتن نتیجهٔ Moviesho نمی‌شود؛ نسخه‌ها
و قسمت‌های جدید همان عنوان هم با نگه‌داشتن متادیتای اصلی ادغام می‌شوند.
دامنهٔ دانلود جدید `sr1moviesho.musitraf.com` نیز شناخته می‌شود. در صفحه‌های
بدون لینک IMDb، فقط تطبیق یکتای نام کامل + نوع + سال فیلم با IMDb موجود در
آرشیو پذیرفته می‌شود؛ سریال هم‌نامِ مبهم انتخاب نمی‌شود.

برای تکمیل هویت موارد نامشخص، بعد از دریافت فایل رسمی و تازهٔ
IMDb می‌توان تطبیق دقیق را جداگانه اجرا کرد:

```bash
node scripts/imdb-exact-source-identities.mjs .media-cache/vod-sync/moviesho-refreshed-report.json .media-cache/vod-sync/imdb-source-identities.json
# در محیط اجرای collector:
# MOVIESHO_IMDB_IDENTITIES=.media-cache/vod-sync/imdb-source-identities.json
```

نام کامل، نوع عنوان و سال انتشار فیلم باید تطبیق داشته باشد.
حذف اپاستروف/اعراب و یکسان‌سازی `&` و `and` فقط نرمال‌سازی نام فایل است؛
جستجوی fuzzy و حدس سال از پوشهٔ آپلود انجام نمی‌شود. ریمیک و سریال هم‌نام مبهم می‌ماند.
تازه‌شدن دیتاست امتیازها به معنی تازه‌شدن جدول ترند IMDb نیست؛
هر دو منبع و خطاهایشان جدا در گزارش ثبت می‌شوند.

دریافت دیتاست حجیم IMDb سقف زمانی دارد؛ هنگام قطعی، کش قبلی فقط برای پرکردن
اطلاعات کمبوددار استفاده می‌شود و امتیاز/سال/عنوان موجود عقب‌گرد نمی‌کند.
برای بازیابی آفلاینِ صریح، `IMDB_DATASET_CACHE_ONLY=1` قابل تنظیم است.

## بازبینی منطقه‌ای ۱ نوامبر ۲۰۲۶

این مرحله روی سیستم محلی انجام شد؛ روی سرور اصلی deploy نشده است.

- دسته‌های ترکی، کره‌ای، ایرانی، انیمه و سریال Moviesho دوباره صفحه‌بندی شدند:
  ۱٬۴۲۶ عنوان یکتا بررسی شد؛ ۱٬۲۹۱ مورد از قبل به‌روز بود و ۱۳۵ صفحهٔ تغییرکرده
  دریافت شد. خروجی واجد فایل ۱۱۸ عنوان بود؛ ادغام، ۹۳ رکورد جدید و ۲٬۶۵۳ لینک اضافه کرد.
- مجموعهٔ اختصاصی `anime` علاوه بر فیلم و سریال خوانده می‌شود. «انیمه» ژانر است،
  نه نوع اثر؛ شمارهٔ قسمت و مسیر/نوع منبع برای تشخیص سریال به کار می‌رود.
- پیمایش MihanDownload از پوشهٔ سال جاری، ۷۶ پوشه را کامل خواند و ۳۳۸ عنوان
  با ۶۰۴ لینک یافت؛ ۳۳۳ رکورد جدید و ۵۹۳ لینک جدید ادغام شد. این‌ها افزوده‌های
  آرشیو هستند، نه ادعای انتشار تازهٔ تمام این فیلم‌ها.
- پیمایش Mihan در کار شبانهٔ `public-archives` و در همان بازهٔ تنظیم‌شدهٔ
  ۰۳ تا ۰۷ تهران اجرا می‌شود. شکست یک آرشیو مانع تلاش برای منابع مستقل نیست.
- پس از پیمایش کامل قبلی F2MY، ۸۰ صفحهٔ تازه نیز بازخوانی شد؛ سه لینک جدید
  برای `tt38647499` ثبت شد. ادغام میزبان تازه، نشانی قبلی را در `sourceLinkHistory`
  برای سابقه نگه می‌دارد، نه به‌عنوان دانلود تأییدشدهٔ فعال.
- از هفت سایت پیشنهادی، FamilyMovie بخشی از جزئیات را پاسخ داد و بخشی timeout شد؛
  وضعیت آن همچنان `partial` است. سایت‌های غیرقابل‌دسترسی، اپلیکیشن‌محور و
  فاقد دانلود عمومیِ قابل‌استخراج، «کامل دریافت‌شده» گزارش نمی‌شوند.
- برای فیلم‌های قدیمی ایرانی، صفحهٔ OITN و کاندیداهای یوتیوب دوباره بررسی شدند،
  اما اتصال اجازهٔ تأیید مدت و پخش کاندیداهای تازه را نداد؛ لینک حدسی اضافه نشد.
  ارجاع‌های رسمی KOFA/NFB با پلیر ناشر، جدا از دانلود مستقیم حفظ شدند.
- فایل‌های رسمی IMDb در ۱ نوامبر دریافت و با خواندن کامل gzip و هدر TSV
  اعتبارسنجی شدند: ۲۵٬۵۸۵ تطبیق اطلاعات پایه و ۲۵٬۵۶۶ تطبیق امتیاز.
  این به معنی تازه‌شدن نمودار محبوبیت IMDb نیست؛ پاسخ‌های challenge آن جدا ثبت‌اند.
- در ۱٬۵۴۸ بررسی تازهٔ Upera، ۲۲۱ پاسخ HTML از دانلود فعال جدا شد؛
  ۱۲ خطای شبکه حذف نشدند. ادغام شبانه لینک HTML تأییدشده را دوباره فعال نمی‌کند.
  این بررسی پاسخ سرور است، نه تضمین کدک یا پخش کامل روی همهٔ دستگاه‌ها.

گزارش قابل‌انتقال در `public/data/source-refresh-report.json` شامل وضعیت منابع،
تفاوت‌های ادغام، شمارش نهایی، بررسی رسانه و ممیزی حفظ آرشیو است.
ممیزی، داده‌های تکراری با IMDb یکسان را در کنار هم ارزیابی می‌کند؛ لینک‌های
امضادار جایگزین‌شده، صفحه‌های دانلود خارجی و منابع قبلی حذف نمی‌شوند و سابقهٔ
آن‌ها با فایل قابل‌پخش اشتباه گرفته نمی‌شود. محدودیت حق‌نشر `tt33184638`
مستقل از دادهٔ اسکرپ‌شده باقی است.

جستجوی سایت و بات از اصلاح عبارت کامل و چیدمان «نزدیکی عنوان ← سال جدیدتر ← IMDb»
استفاده می‌کنند. نام دقیق از عنوانی که فقط بخشی از آن تطبیق دارد بالاتر می‌ماند.
سورت صریح امتیاز/سال در بات همچنان انتخاب کاربر را رعایت می‌کند.
پنجرهٔ جستجوی موبایل تمام‌صفحه است؛ نتایج فیلم منتظر پاسخ کند موسیقی نمی‌مانند.

سایت‌مپ عمومی همچنان `/sitemap.xml` و بخش‌ها `/sitemap/0.xml` و ... هستند.
هندلر صریح بخش‌ها جای تداخل route و metadata قبلی را گرفته است؛ آدرس‌ها تغییر نکردند.

## تست بازبینی

```bash
node --test scripts/tests/public-vod-sources.test.mjs scripts/tests/donyaye-archive.test.mjs scripts/tests/curated-merge-identity.test.mjs scripts/tests/maintenance.test.mjs scripts/tests/scraper-dashboard-config.test.mjs
node --import tsx --test scripts/tests/typo-search.test.ts scripts/tests/bot-api.test.ts scripts/tests/sitemap-xml.test.ts scripts/tests/content-restrictions.test.ts
# با Playwright نصب‌شده، در صورت نیاز PLAYWRIGHT_MODULE را به فایل index.mjs بدهید:
LOAD_BASE_URL=http://127.0.0.1:3004 node scripts/smoke-discovery-search.mjs
```

این تغییرات به درخواست مالک فقط در Git منتشر می‌شوند؛ اجرای ابزار روی
سیستم محلی به معنی deploy شدن یا اجرای زمان‌بند روی سرور نیست.

فایل‌های بزرگ `vod-catalog.json`، `vod-people.json`، `music-index.json` و
`music-artists.json` با Git LFS منتقل می‌شوند. روی ماشین انتشار، بعد از
دریافت commit و پیش از build، `git lfs pull` را اجرا کنید. ابتدا از دادهٔ
زندهٔ سرور پشتیبان بگیرید؛ فایل‌های آرشیو زنده را برای تمیزکردن Git حذف نکنید.

**RAM پیش از انتشار:** فهرست کامل موسیقی این نوبت بیش از ۲۲۰MB شده است؛
آزمایش محلی خواندن آن حدود ۱GB RSS مصرف کرد. سقف قدیمی heap کانال (۱GB)
برای این داده و سایر فهرست‌ها حاشیهٔ امن ندارد. Composeهای کانال و نسخهٔ
production برنامه برای آرشیو بزرگ‌تر تنظیم شده‌اند. قبل از اجرای آن‌ها
ظرفیت آزاد میزبان را بررسی کنید؛ هیچ تغییری در سرور زنده اعمال نشده است.

```dotenv
APP_HEAP_MB=2304
APP_MEMORY_LIMIT=3g
TELEGRAM_CHANNEL_HEAP_MB=2048
TELEGRAM_CHANNEL_MEMORY_LIMIT=3g
MAINTENANCE_MAX_MEMORY_MB=2304
```

آستانهٔ RSS زمان‌بند هم با این ظرفیت هماهنگ شده تا کش بزرگ‌تر موسیقی باعث
توقف دائمیِ بررسی شبانه در زمان کم‌ترافیک نشود. override صریح قبلی در `.env`
محفوظ است و باید با RAM میزبان بازبینی شود.

هنگام یکی‌شدن نسخهٔ تکراری آهنگ‌ها، شناسه‌های قبلی در `idAliases` باقی
می‌مانند و صفحهٔ موسیقی آن‌ها را می‌شناسد؛ قطعهٔ قدیمیِ بدون جایگزین هم حذف
نمی‌شود. برای یک‌بار تطبیق با یک بکاپ قبلی می‌توان از
`node scripts/stable-music-identities.mjs --baseline=/path/to/music-index-backup.json`
استفاده و سپس indexهای موسیقی را بازسازی کرد.
